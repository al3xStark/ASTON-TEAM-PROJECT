# Руководство для участников команды

Этот файл описывает правила работы с репозиторием.

---

## Первая команда при любом сомнении

Не понимаешь что происходит? Не знаешь в какой ветке находишься? Что-то пошло не так?

```bash
git status
```

Эта команда показывает: в какой ты ветке, какие файлы изменены, что готово к коммиту, а что нет. Она ничего не меняет — только показывает текущее состояние. Запускай её в любой непонятной ситуации, это всегда безопасно.

---

## Структура веток

В проекте используются три уровня веток:

```
main          ← финальная версия проекта
└── develop   ← рабочая ветка, сюда вливаем выполненные задачи
    ├── feature/task-1
    ├── feature/task-2
    ├── feature/task-3
    └── feature/task-4
```

**Главные правила:**
- Никогда не пушим напрямую в `main` и `develop`
- Вся работа ведётся в своей `feature/`-ветке
- В `main` вливаем один раз в самом конце, когда всё готово

---

## Именование веток

Формат: `feature/название-задачи`

Только латиница, слова через дефис, всё строчными буквами.

**Примеры:**
```
feature/insertion-sort
feature/merge-sort
feature/manual-input
feature/file-input
feature/random-menu
```

---

## Начало работы над задачей

Каждый раз перед началом работы выполняй эти шаги по порядку. Это важно — иначе твоя ветка будет отставать от `develop` и возникнут конфликты.

```bash
# 1. Переходим на develop
git checkout develop

# 2. Скачиваем изменения с GitHub
git fetch origin

# 3. Применяем изменения
git merge origin/develop

# 4. Создаём свою ветку от develop
git checkout -b feature/название-задачи
```

Всё, можно работать.

---

## Коммиты

Один коммит — одно изменение. Не накапливай всю работу за день в один коммит.

**Формат сообщения:**
```
[тег] краткое описание что сделано
```

**Теги:**
- `[feat]` — новая функциональность
- `[fix]` — исправление ошибки
- `[test]` — тесты
- `[refactor]` — правки кода без изменения поведения

**Примеры:**
```
[feat] добавлен алгоритм сортировки вставками
[fix] исправлена валидация года производства
[test] тесты для CarValidator
[refactor] переименованы методы в SortContext
```

## Создание Pull Request

Когда задача готова:

**1. Пушим ветку на GitHub:**
```bash
git push origin feature/название-задачи
```

**2. Открываем Pull Request на GitHub:**
- Заходим в репозиторий
- GitHub покажет баннер с кнопкой **"Compare & pull request"** — нажимаем
- Проверяем направление: `base: develop` ← `compare: feature/твоя-ветка`
- Пишем заголовок по той же логике что и коммиты, например: `[feat] алгоритм сортировки вставками` или `[feat] ручной ввод и валидация`
- В описании — что изменилось, есть ли вопросы или что-то незаконченное
- В разделе **Reviewers** назначаем тимлида
- Нажимаем **"Create pull request"**

**3. Ждём ревью.**

Самостоятельно принимать PR не нужно — это делает тимлид после проверки кода.

**4. Если тимлид запросил правки:**

Не закрывай PR и не открывай новый. Просто внеси правки в ту же ветку и запушь:

```bash
git add .
git commit -m "[fix] правки после ревью"
git push origin feature/название-задачи
```

PR на GitHub обновится автоматически.

**5. После того как PR принят:**

Ветка больше не нужна. Удали её локально, чтобы не копились мёртвые ветки:

```bash
git checkout develop
git branch -d feature/название-задачи
```

Если Git выдал ошибку — замени -d на -D, это нормально после принятого PR.

## Синхронизация с develop

Пока ты работаешь над своей задачей, другие участники могут влить свои изменения в `develop`. Чтобы твоя ветка не отставала, периодически подтягивай изменения.

```bash
# Скачиваем изменения с GitHub, но ещё не применяем
git fetch origin

# Смотрим что изменилось в develop с момента последнего fetch —
# команда выводит список новых коммитов в одну строку каждый
git log origin/develop --oneline

# Переходим на develop и применяем скачанные изменения
git checkout develop
git merge origin/develop

# Возвращаемся в свою ветку и вливаем в неё обновлённый develop
git checkout feature/название-задачи
git merge develop
```

Важно: последняя команда `git merge develop` — это обновление твоей рабочей ветки, не финальный merge задачи. Финальное вливание делает тимлид через PR.

Делай синхронизацию хотя бы раз в день, если активно работаешь.

## Конфликты

### Почему они возникают

Конфликт происходит когда два человека изменили один и тот же файл в разных ветках, и Git не может автоматически решить чью версию оставить.

### Как выглядит конфликт

После команды `git merge` в конфликтном файле появятся такие маркеры:

```
<<<<<<< HEAD
    // твоя версия кода
=======
    // версия из develop
>>>>>>> develop
```

Это не поломка. Git просит тебя выбрать что оставить.

### Как разрешить

1. Открой конфликтный файл в IDE
2. Найди маркеры `<<<<<<<`, `=======`, `>>>>>>>`
3. Оставь нужный код, удали маркеры
4. Сохрани файл
5. Выполни:
```bash
git add .
git commit -m "[fix] разрешён конфликт в НазваниеФайла.java"
```

### Главное правило

Если не уверен что делать — не угадывай. Напиши тимлиду в чат, разберём вместе. Конфликты решаются, ничего безвозвратно не ломается.

## Работа с GitHub Project
 
В проекте используется канбан-доска с четырьмя колонками: **Backlog**, **In Progress**, **In Review**, **Done**.
 
**Правило простое: статус задачи на доске всегда отражает реальное состояние твоей работы.**
 
### Когда что переносить
 
| Колонка | Когда переносить |
|---|---|
| **Backlog** | Задача назначена, но ты ещё не начал |
| **In Progress** | Ты начал работу — создал ветку и сделал первый коммит |
| **In Review** | Ты открыл Pull Request и назначил тимлида ревьюером |
| **Done** | Тимлид принял PR, задача влита в develop |
 
### Как взять задачу
 
1. Зайди в GitHub Project
2. Найди свою задачу в **Backlog**
3. Открой её и назначь себя в поле **Assignees**
4. Когда начинаешь работу — переноси в **In Progress**
5. Когда открыл PR — переноси в **In Review**
 
Перемещать карточку в **Done** самостоятельно не нужно — это сделает тимлид когда примет PR.

### Лейблы
 
У каждого issue есть два лейбла — **приоритетность** и **тип**:
 
| Лейбл | Что означает |
|---|---|
| `core` | Основная задача, без которой проект не работает |
| `extra` | Дополнительное задание |
| `feat` | Новая функциональность |
| `test` | Тестовый класс |
| `bug` | Исправление ошибки |
 
Примеры комбинаций: `core` + `feat`, `core` + `test`, `extra` + `feat`, `core` + `bug`.
 
Лейблы проставляются при создании issue в поле **Labels** на правой панели. Если создаёшь issue сам — не забудь поставить оба лейбла сразу.
 
---
 
### Если нашёл баг или увидел проблему
 
Не держи в голове и не пиши только в чат — создай issue:
 
1. Зайди во вкладку **Issues** репозитория
2. Нажми **New issue**
3. Заголовок — по той же логике что и коммиты, например: `[bug] NPE в FileInputHandler при пустом файле`
4. В описании — что происходит, как воспроизвести, что ожидалось
5. Поставь лейблы: `core` или `extra` + `bug`
6. В поле **Assignees** назначь себя, если берёшь в работу, или оставь пустым — тимлид распределит
7. Нажми **Submit new issue**
 
---
 
Написать тимлиду в чат — это всегда правильное решение. Лучше спросить лишний раз, чем потерять работу или сломать ветку.
